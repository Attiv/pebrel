## 修 v2.2.4 release 在 ubuntu-24.04 上的 native test 失败

**现象**：`Attiv/pebrel` 的 v2.2.4 stable release run（38213334657）只有
`native-tests / Native tests (ubuntu-24.04)` 真挂——其余 4 个平台全过。
挂的是两个光标轨迹用例：
`cursor::tests::blink_phase_...`（tests.rs:209 `motion.active()`）与
`cursor::tests::cursor_motion_hot_applies_...`（tests.rs:44 `visual_cursor` 期望 (0,0)
实得 (4,0)）。下游 aggregate job 与 `Publish verified GitHub Release` 因此被带挂/跳过。

**根因**（不是 flake，是确定性的跨进程竞态）：
- `open()`（`terminal/view/startup_tests.rs`）用 `Settings::load()` 读**真实设置文件**
  （`~/.config/pebrel/pebrel_settings.txt`；macOS 为 `~/Library/Application Support/Pebrel/`）。
- `visual_cursor` 的 `enabled` 门里有 `animations_enabled(cx)`，它读 `Settings.animations`。
- `gpui_shell/settings_pane/tests.rs::animation_effects_switch_is_visible_in_appearance_and_persists`
  在运行期间把 `animations=0` **持久化进同一个共享文件**，只在 Drop 时才还原字节。
  `.config/nextest.toml` 的 `theme-studio` 组只把夹具**互相**串行，不隔离组外的读者。
- 那两个用例钉了 `cursor_motion` 却没钉 `animations`，于是结论取决于磁盘上恰好是什么字节。

**复现手法（关键技巧，可复用）**：`paths.rs` 支持 `PEBREL_CONFIG_DIR` 覆盖；
把它指到一个 `pebrel_settings.txt` 内容为 `animations=0` 的临时目录 → 6 个轨迹用例
+ `details_panel::tests::switching_to_instant_removes_closed_panel_geometry` 全挂，
panic 位置和数值与 CI 完全一致；换成 `animations=1` 全过。**不用改用户真实配置**。

**改动**（只 3 个文件）：
- `cursor/tests.rs`：新增 `smooth_motion(cx)` 辅助（同时钉 `cursor_motion=Smooth` 与
  `animations=true`），替换 6 处旧赋值。
- `details_panel_tests.rs`：`switching_to_instant_...` 就地 `settings.animations = true`
  （同文件另两个用例本来就是这写法）。
- 新增 note `architecture/notes/nebula_app/gpui_shell/settings_fixture/2026-10-12-trajectory-motion-declares-its-own-animation-gate.md`。

**验证**：`animations=0` + `PEBREL_CONFIG_DIR` 隔离下，
`cargo test -p nebula --bin pebrel` 2313 passed/0 failed；`--workspace` 全绿；
`cargo fmt --all -- --check` 通过；lint job 那 7 个 CI 契约模块 91 tests OK。

## 更正：`PENDING FINAL BUILD` 是设计，不要去回填（2026-10-12 复核）

上一条待办里"回填 docs/release-notes/v2.2.5.md 与 CHANGELOG 的哈希"是**错的**，已撤销。

读 `scripts/stable_release.py` 得到的事实：
- 第 23 行定义了 `PENDING_SHA256 = "PENDING FINAL BUILD"`，`validate_notes()`
  明确把它列为**合法**的 SHA256 占位形式（与 `<!-- STABLE_SHA256 -->` 并列，可三选一）。
- `render_notes()`（243-265 行）在 CI 构建时把 `checksum_text()` 的真实摘要替换进占位符，
  产物是 `release-dist/RELEASE_NOTES.md`，而 `release.yml:740` 的
  `gh release create --notes-file release-dist/RELEASE_NOTES.md` 用的就是它。
- 因此**线上 Release 正文带真实哈希，仓库里的 docs 文件保留占位符**是预期形态。
- 佐证：`docs/release-notes/v2.2.2.md`、`v2.2.3.md` 至今仍是 `PENDING FINAL BUILD`，
  而其 Release 已公开发布。历史先例从未回填过。
- 反向风险：真去回填，`render_notes()` 会走第三分支（无占位符时逐行比对
  `f"{digest}  {name}"` 是否原样出现在 notes 里）；格式稍有出入反而会让下次发布硬失败。

结论：**发布后不需要改任何文档**。该做的是独立复核线上 Release 本身
（packaging/AGENTS.md 第 9 行），复核脚本写在 `/tmp/pebrel-release-verify/verify_release.py`，
资产清单从 `scripts/stable_release.py::expected_asset_names` 复制一份冻结副本对照
（已验证 2.2.5 → 11 项，与仓库逐项相同）。

## ⚠️ 更正：遥测上传**不是**缺陷，别加 continue-on-error（12:40Z 复核后推翻）

上面「仓库真实缺陷」那一节是我**读得不够就下的结论，已推翻**。三条硬证据：

1. `scripts/tests/test_stable_release.py:116` 的 `self.assertNotIn("continue-on-error", shared)`，
   其中 `shared` = **整个 `.github/workflows/linux-lua.yml` 文件内容**（第 95 行读入）。
   在该文件**任何位置**加 `continue-on-error` 都会打挂
   `test_stable_workflow_requires_same_commit_native_tests_before_publication`。
   同文件第 137 行还有负向变异 `("  native-tests:\n", "  native-tests:\n    continue-on-error: true\n")`
   专门证明这条断言真的有效。同理 `test_ci_native_tests.py:49/241/259`、
   `test_android_release.py:232` 也各自禁止。
2. `scripts/AGENTS.md:5` 的明文规则：**「不通过提高预算、扩大排除、自动加例外、删除测试或
   `continue-on-error` 消除失败。规则错误时提交窄范围政策修订和回归。」**
3. `architecture/notes/packaging/2026-10-07-tag-native-publication-gate.md` 的 Validation 段：
   「Negative mutations remove the native prerequisite, substitute another workflow,
   disable the call or **ignore errors**; each is rejected.」

**我先前把 `if: always()` 读成了「尽力而为、不该阻塞」。这是误读**：`always()` 的语义是
「**即使前面步骤失败也要执行**」—— 目的是让测试失败时仍留下 cargo 计时诊断（覆盖失败场景），
而**不是**声明这一步可忽略。让遥测上传在 artifact 服务不可用时把 job 打红，
与这份被测试锁定的设计是**自洽的**，并非"意图与实现不一致"。

**结论：不改 workflow。** 想要它非阻塞，就必须走 `scripts/AGENTS.md` 授权的路径 ——
**窄范围政策修订 + 同步更新回归测试 + 一份 packaging 决策 note**，而不是顺手加一行。
是否要做由用户决定，不擅自推翻被测试锁定的政策。
